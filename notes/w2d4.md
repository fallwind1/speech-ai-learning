# W2D4 模块1：Checkpoint概念

## 1.1 什么是 Checkpoint

Checkpoint：

> 训练检查点/训练状态快照：把当前训练实验状态整体保存下来。

它保存的是：

> 当前训练实验状态，例如：
> 模型参数是多少？
> optimizer里面保存了什么？
> 当前训练到第几轮？
> 随机状态是什么？
> 实验配置是什么？

---

## 1.2 为什么需要 Checkpoint

没有 checkpoint：

```text
训练到 Epoch 10

↓

程序中断

↓

结果：
不知道已经训练10轮，从epoch0重新开始记录
```

有 checkpoint：

```text
训练到 Epoch 10

↓

保存状态

↓

程序中断

↓

加载

↓

从epoch 10 附近继续训练
```

---

## 1.3 为什么不能只保存模型参数

只保存：

```python
model.state_dict()
```

可以恢复：

> 模型参数

但是不能恢复：

> 当前训练状态

---

## 1.4 一次完整训练状态包含什么

通常包括：

```text
model:
模型参数

optimizer:
例如SGD：- 当前学习率；- momentum缓存

epoch:
训练轮数

config:
例如：学习率、batch-size、隐藏层特征

random seed:
随机种子，影响：
- 初始化参数；
- shuffle顺序；
- 随机采样
```

---

## 1.5 Model 参数和训练状态区别

模型参数：

> 回答模型现在是什么样（例如：weight、bias）

训练状态：

> 回答训练过程现在进行到哪里，包括:optimizer epoch config seed

二者关系：

> 想要完整恢复，需要二者结合

---

## 1.6 Checkpoint核心思想

一句话总结：

> checkpoint保存训练过程某个时间点的完整状态，使训练能够暂停、恢复，并提高实验管理能力。


# W2D4 模块2：state_dict()

## 2.1 什么是 state_dict()

state_dict：

> 状态字典

它本质上是：

> 保存模型或优化器状态的Python字典结构，例如：
{
    "layer1.weight": tensor(...),
    "layer1.bias": tensor(...)
}

---

## 2.2 model.state_dict()

代码：

```python id="n3b5qv"
model.state_dict()
```

返回：

> 一个包含模型参数和模型状态的字典

例如：

```text id="2x7w9n"
{
    "layer.weight":tensor(...),
    "layer.bias":tensor(...)
}
```

其中保存：

> 可学习参数、buffer（例如：BatchNorm running_mean、running_var）

不保存：

> 模型结构代码、optimizer、epoch等

---

## 2.3 为什么保存 state_dict 而不是直接保存 model

直接保存：

```python id="q6h7pm"
torch.save(model, "model.pt")
```

问题：

> 若模型代码更改，则再加载旧模型可能出现结构不匹配。

state_dict方式：

```python id="m7k2pz"
保存：

model.state_dict()

加载：

先重新创建结构model=MLP()，然后model.load_state_dict(...)
```

优点：

> 代码控制结构、文件保存参数，职责分离。

---

## 2.4 optimizer.state_dict()

optimizer.state_dict()

保存：

> 优化器内部状态

例如：

```text id="4z8s6h"
{

    {...}

    param_groups:
    {...}
}
```

# W2D4 模块4：加载 Checkpoint 与 Resume Training

## 4.1 恢复训练的基本流程

```text
checkpoint文件
↓
torch.load()
↓
重新创建 model / optimizer
↓
load_state_dict()
↓
恢复训练进度
↓
从下一epoch继续训练
```

为什么必须先创建 model 和 optimizer：

> 因为没有保存模型结构和优化器对象

---

## 4.2 加载 Checkpoint

代码：

```python
checkpoint = torch.load(
    CHECKPOINT_PATH,
    weights_only=True,
)
```

如果需要指定加载设备：

```python
checkpoint = torch.load(
    CHECKPOINT_PATH,
    map_location="cpu",
    weights_only=True,
)
```

`torch.load()` 的作用：

> 读取由torch.save()保存的对象

`map_location` 的作用：

> 加载Tensor时，把它映射到指定设备

---

## 4.3 恢复 Model

代码：

```python
model.load_state_dict(
    checkpoint["model_state_dict"]
)
```

恢复后：

> model中的参数和保存checkpoint时的模型状态一致

`load_state_dict()` 是否重新创建模型结构：

> 不

---

## 4.4 恢复 Optimizer

代码：

```python
optimizer.load_state_dict(
    checkpoint["optimizer_state_dict"]
)
```

恢复的是：

> 优化器状态

如果不恢复 optimizer：

> 没有历史状态

---

## 4.5 恢复 Epoch

保存：

```python
"epoch": epoch
```

加载：

```python
saved_epoch = checkpoint["epoch"]

start_epoch = saved_epoch + 1
```

如果 checkpoint 保存的是“刚完成的 epoch”，为什么通常从下一轮继续：

> 因为当前epoch已经训练过

---

## 4.6 恢复 Config 与 Seed

```python
config = checkpoint["config"]

seed = checkpoint["seed"]
```

作用：

```text
config →
恢复和确认实验配置

seed →
恢复和记录实验使用的随机种子
```

---

## 4.7 验证恢复后参数一致

保存前参数：

```python
before = {
    name: param.detach().clone()
    for name, param in model.named_parameters()
}
```

加载后检查：

```python
for name, param in model.named_parameters():
    assert torch.equal(before_params[name],param)
```

如果全部通过：

> 保存前参数=加载后参数
这里使用：

param.detach().clone()

是为了：

创建一个不参与 autograd、且独立于原参数 Tensor 的参数副本，用于后续比较。

---

## 4.8 Resume Training

```python
for epoch in range(
    start_epoch,
    config["epochs"],
):
    train_one_epoch(...)
```

恢复训练前：

```python
model.trainMLP(...)
```

作用：

> 将模型切换回训练模式，使模型按照训练阶段的行为运行。

---

## 4.9 本模块核心结论

模型恢复：

> 先创建兼容的模型结构，再通过 model.load_state_dict() 恢复模型参数和 buffer。

优化器恢复：

> 先创建 optimizer，再通过 optimizer.load_state_dict() 恢复优化器的历史状态和参数组配置。

epoch恢复：

> 如果 checkpoint 记录的是最后一个已经完成的 epoch，则使用 saved_epoch + 1 作为恢复训练的起点。

参数一致性验收：

> 保存前复制模型参数，加载后使用 torch.equal() 与恢复参数逐项比较；全部严格相等说明模型状态恢复成功。

一句话总结：

> Resume training 的本质是重新创建模型和优化器对象，把 checkpoint 保存的状态重新装回这些对象，再恢复训练进度，从中断位置继续训练。


# W2D4 模块5：随机种子与可复现边界

## 5.1 Seed 的作用

```python
torch.manual_seed(SEED)
```

作用：

> 设置随机数生成的seed，使相同条件下的随机过程更容易重复。

固定 seed 主要用于：

> 模型随机初始化
Dataset随机划分
DataLoader shuffle
随机采样
Dropout

固定 seed 是否保证任何环境下结果完全一致：

> 不保证，seed 只能控制随机过程的一部分，浮点计算、CUDA、硬件、软件版本和非确定性算法等仍可能造成差异。

---

## 5.2 Seed 与 RNG State

Seed 可以理解为：

> 随机序列最初从哪里开始，即随机过程的初始起点

RNG state 可以理解为：

> 随机数生成器当前走到哪里，即随机过程当前所在的位置

如果训练已经产生了很多随机数，只保存最初的 seed：

> 可能在一轮epoch中使用了很多随机数，因此RNG走了很远，重启后又重新回到随机序列开头

如果希望更严格地从中断点恢复随机过程：

> 额外保存RNG state

---

## 5.3 训练中的随机来源

常见随机来源：

```text
1. 模型参数随机初始化

2. DataLoader shuffle / 数据随机划分

3. Dropout等随机操作


4. Python / NumPy / PyTorch中的随机采样
```

这些随机过程可能影响：

> 输入batch顺序、模型前向结果、梯度以及参数更新，从而改变后续训练轨迹。

---

## 5.4 浮点计算为什么存在误差

浮点数特点：

> 有限精度，float32大约7位十进制有效数字

浮点运算是否严格满足结合律：

> 不满足

因此：

```text
(a + b) + c

与

a + (b + c)
```

在计算机上：

> 存在差异，但非常小

---

## 5.5 CPU / GPU / 硬件差异

即使：

```text
相同代码
相同参数
相同输入
相同 seed
```

不同硬件上的结果：

> 仍可能不同

原因包括：

> CPU时按某种顺序计算（(((a+b)+c)+d)...，而GPU能够大量并行计算再合并，而浮点运算不严格满足结合律，所以结果可能不同。

---

## 5.6 Deterministic Algorithm

可以使用：

```python
torch.use_deterministic_algorithms(True)
```

作用：

> 当存在确定性算法时，要求PyTorch使用确定性实现

如果某个操作没有确定性实现：

> 默认可能直接报RuntimeError

是否仅设置这一项就能保证完整实验 100% 可复现：

> 不能

---

## 5.7 参数一致与训练轨迹一致

Checkpoint 刚恢复后：

```text
保存前 parameters
vs
加载后 parameters
```

应该：

> 严格一致，因为此时只是把保存的Tensor状态重新读取回来，还没有继续新的训练计算。

可以使用：

```python
torch.equal(
    before,
    restored
)
```

继续训练后比较：

```text
run A
vs
resumed run B
```

可能需要：

```python
torch.allclose(
    tensor_a,
    tensor_b,
    rtol=...,
    atol=...
)
```

原因：

> 后续训练可能受到随机过程、浮点计算、CUDA并行、硬件和软件环境等影响，产生合理范围内的微小数值差异。

---

## 5.8 本次实验的可复现声明

本次实验尽量固定：

```text
seed =
42

PyTorch version =
记录实际运行版本

device =
记录实际CPU/GPU

model/config =
保持模型结构、学习率、batch-size等配置一致
```

实验结论应该表述为：

> 在相同代码、软件版本、硬件、随即设置和确定性配置下，实验应具有较强可复现性；但由于浮点精度、并行计算和不同底层实现等因素，不应默认保证跨硬件或跨软件环境逐位完全一致。

---

## 5.9 本模块核心结论

一句话：

> 可复现不仅仅是设置一个seed，而是需要控制随机源、必要时恢复RNG state、保存完整训练状态并尽量固定运行环境；即使如此，浮点精度、CUDA并行和硬件差异仍可能导致微小数值差异，因此训练结果应在明确的环境和容差范围内讨论可复现性。

## 6.2 保存函数

def save_checkpoint(...):
    checkpoint = {
        "model_state_dict": model.state_dict(),
        "optimizer_state_dict": optimizer.state_dict(),

作用：

> 将模型状态、优化器状态、训练进度和实验配置保存成checkpoint文件，为之后恢复训练提供完整状态。

## 6.6 为什么固定每个 Epoch 的 DataLoader 随机顺序

方法：

```python
generator.manual_seed(
    config["seed"] + epoch
)
```

作用：

> 不同 epoch 使用不同随机顺序，但同一个 epoch 在 uninterrupted training 和 resumed training 中使用相同随机 seed，因此得到相同的 shuffle 顺序。

---

## 6.7 W2D4 最终验收

Checkpoint 是否包含：

```text
model:model_state_dict
optimizer:optimizer_state_dict
epoch:当前最后完成的 epoch
config:实验配置
seed:实验随机种子
```

加载后参数是否严格一致：

> 严格一致

恢复后是否从正确 epoch 开始：

> 是

后续训练轨迹：

> 在相同代码、软件环境、模型配置、数据顺序和随机设置下，resumed training 应与 uninterrupted training 相同或仅存在声明容差范围内的微小数值差异。

---

## 6.8 本日核心结论

一句话：

> Checkpoint的本质是保存一次训练实验在某个时间点的完整状态；真正的断点恢复需要重新创建模型和优化器、加载各自的state_dict、恢复下训练进度，并通过参数严格一致性和后续训练轨迹比较验证恢复过程是否正确。
