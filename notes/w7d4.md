# W7D4 模块1：中英混合 ASR 计分原理

## 1. 为什么需要不同计分指标

为什么英文 WER 不适合直接用于中文：
英文通常通过空格区分单词，而中文通常没有词间空格。

为什么中文 ASR 可以使用 CER：
中文通常以单个汉字作为自然的基础计分单位。
CER使用字符级编辑距离，不依赖中文分词算法，可以避免不同分词方式影响评分结果。
对于中英混合文本，CER也可以统一计算，但英文单词会被拆成多个字符，因此较长的英文术语可能具有更大的权重。

为什么中英混合场景需要 MER：
技术讲座中经常同时包含中文、英文技术术语和数字。
如果全部按字符计分，英文单词会被拆分成多个字母；如果全部按英文单词计分，又无法合理处理没有空格的中文。
因此，本项目定义MER的计分单位：

- 中文：逐字。
- 英文：按词。
- 数字：连续数字串作为 token。
- 其他有效符号：使用明确的 fallback 规则保留。

这样可以更合理地反映中英混合语音中的识别错误。

## 2. CER

CER 的计分单位：
Character Error Rate，字符错误率，使用规范化文本去除计分空白后的Unicode字符作为计分单位。

CER 的计算公式：
$$
\boxed{CER=\frac{S_c+D_c+I_c}{N_c}}
$$
其中：

- S_c：字符替换次数。
- D_c：字符删除次数。
- I_c：字符插入次数。
- N_c：Reference 的总字符数。

英文单词在 CER 中如何处理：
英文单词会按照字符拆分

数字串在 CER 中如何处理：
数字串同样按照字符拆分

## 3. MER（项目定义）

MER 的计分单位：
本项目采用混合粒度token：

- 单个中文字。
- 连续英文单词。
- 连续数字串。
- 其他有效符号按照明确规则处理。

中文字符如何划分：
一个中文字符作为一个token

连续英文单词如何划分：
连续英文字母组成的单词作为一个token

连续数字串如何划分：
连续数字作为一个token

MER 的计算公式：
$$
\boxed{MER=\frac{S_m+D_m+I_m}{N_m}}
$$
其中：

- S_m：混合 token 替换次数。
- D_m：混合 token 删除次数。
- I_m：混合 token 插入次数。
- N_m：Reference 中混合 token 的总数。

MER 与 CER 的主要区别：
两者使用相同的编辑距离算法，但token划分粒度不同。

## 4. 英文 WER 与评分规范

英文 WER 的计分单位：
英文单词
$$
WER=\frac{S_w+D_w+I_w}{N_w}
$$
其中 N_w 为 Reference 的英文词数。

为什么英文 WER 要单独报告：
因为中英混合场景的CER和MER无法单独说明模型在纯英文语音上的识别表现。
因此，按照05文档，英文WER应在英文子集上单独计算和报告。
不能直接将中英混合文本简单提取英文词后，就将结果称为标准英文WER。

normalize_score() 的作用：
将原始转写文本转换为统一的评分文本，是项目评测的唯一规范化入口。
主要包括：

- Unicode NFKC 规范化。
- 英文转换为小写。
- 按预先约定处理标点。
- 折叠多余空白，保留单词边界。
- 不自动合并阿拉伯数字与中文数字。
- 不自动将翻译、缩写全称或近音词视为相同。
- 不静默丢弃未知符号。

为什么 Reference 和 Hypothesis 必须采用相同的评分规范：
因为ASR评估的目标是衡量真实识别差异，而不是两种文本处理方式之间的差异。
因此，Reference 与 Hypothesis 必须通过同一套 normalize_score() 规则处理。

为什么不能静默删除未知符号：
因为某些符号具有实际语义，删除它们可能掩盖模型的识别错误

因为中文通常没有词间空格，直接使用split()可能将整句中文视为一个token。

Q2：为什么同样是将 ASR 识别成 LLM，CER 可能统计为3次替换，而 MER 只统计为1次替换？
因为CER按字符计分，MER 将 ASR 和 LLM 分别视为一个英文词 token，因此只需要1次替换。

# W7D4 模块2：文本规范化与中英混合分词

## 1. normalize_score 的作用

为什么需要文本规范化：
ASR的Reference和Hypothesis可能存在大小写、全角与半角、标点、空白等书写差异。
这些差异不一定代表实际的语音识别错误。如果不统一处理，可能使CER、MER等评估结果受到文本格式的干扰。
因此，评分前需要使用固定规则进行文本规范化。

normalize_score 的输入与输出：
输入：原始字符串。
输出：按照项目评分规范处理后的字符串。

为什么 ref/hyp 必须使用同一函数：
Reference 和 Hypothesis 必须采用相同的文本处理规则，才能进行公平比较。
如果只处理其中一侧，就可能引入额外的评分误差。

为什么需要保存 raw_text：
raw_text 保存原始转写内容，score_text 保存规范化后的评分文本。
规范化可能改变大小写、标点或其他兼容字符。
保留 raw_text 可以用于人工核查、恢复原始书写信息和审计评分规则。

## 2. 文本规范化规则

NFKC 的作用：
NFKC使Unicode兼容规范化形式，用于统一某些具有兼容关系的字符表示。

英文小写处理：
使用text.lower()将英文字母统一为小写。

空白折叠：
text = " ".join(text.split())
将连续空格、换行、制表符等普通空白统一为一个空格，并去掉首尾空白。

普通标点处理：
本模块的v1草案将约定的普通逗号、句号、问号等标点转换为空格，使这些标点不参与主指标计分，同时尽可能保留词边界。

数字处理：
将连续数字串作为一个MER token

技术术语与特殊符号处理：
本模块为以下表达制定了初步规则：
C++     → c++
C#      → c#
GPT-4   → gpt-4
v1.2.3  → v1.2.3
3.14    → 3.14
这些表达在 mixed_tokens() 中保留为完整 token。

为什么未知符号不能静默丢失：
因为某些符号具有实际语义，删除它们可能掩盖 ASR 的识别错误。

## 3. mixed_tokens 的实现原理

mixed_tokens 的输入与输出：
输入：原始字符串或待规范化字符串。
输出：按照项目 MER 规则划分的 token 列表。
当前实现会在函数内部调用 normalize_score()。

中文字符的处理：
中文逐字划分。

连续英文字符的处理：
连续英文单词作为一个token

连续数字的处理：
连续数字串作为一个token

C++、C#、GPT-4、版本号的处理：
本次实现优先匹配完整的技术表达。

其他有效符号的 fallback：
正则表达式最后使用：r"|[^\s]"，表示前面的规则无法识别时，保留一个非空白字符。

为什么正则表达式的匹配顺序很重要：
正则表达式中|表示多个候选模式，Python的re通常优先尝试靠左的可匹配分支。因此，需要先放置完整英文词、技术表达和数字规则，再放置单字符fallback。

## 4. normalize_score 与 mixed_tokens 的关系

两个函数的执行顺序：
评分处理流程：
原始文本
   ↓
normalize_score()
   ↓
规范化字符串
   ↓
mixed_tokens()
   ↓
混合 token 序列
   ↓
score_tokens() / score_corpus()
   ↓
MER

为什么不能直接使用 split()：
因为中文通常没有词间空格。
直接 split() 可能把完整中文句子视为一个 token，无法合理反映中文字的识别错误。
另外，split() 也不能自动完成 NFKC、数字串和技术符号处理。

为什么不能直接删除所有非字母数字字符：
这会丢失技术符号、未知字符和英文词边界。

CER 与 MER 如何复用这两个函数：
CER：
先调用 normalize_score()，然后按照05文档去除计分空白，将剩余 Unicode 字符逐个作为 token，最后使用 score_tokens() 或 score_corpus() 计算字符错误率。

MER：
调用 mixed_tokens() 得到中文单字、英文词、数字串及有效符号 token，再使用相同的编辑距离算法计算错误率。
两者不需要分别实现新的 DP 算法，区别主要在于输入 token 的划分方式。

## 6. 模块验收

Q1：normalize_score() 为什么要先执行 NFKC，再执行小写转换？NFKC 和小写转换解决的是同一种问题吗？
不是，NFKC用于统一Unicode兼容字符的表示形式，例如将全角英文字母转换为普通英文字母。
小写转换用于统一字母的大小写，例如将Python转换为python。


Q2：为什么将 hello,world 中的逗号替换为空格，而不是直接删除？
因为逗号可能起到分隔两个单词的作用，如果直接删除，两个英文单词被错误合并。

Q3：mixed_tokens() 中的正则表达式为什么需要设置不同的匹配优先级？如果优先按单个字符匹配，会发生什么？
因为不同类型的内容需要按照不同的粒度划分。
完整英文词、数字串、技术表达应该优先匹配。
如果单字符规则优先，可能把完整单词或技术表达拆开，导致 MER 的计分单位错误。

Q4：为什么不能使用 re.sub(r"[^a-zA-Z0-9\u4e00-\u9fff]", "", text) 清洗文本？
因为该正则表达式会删除所有不属于指定英文、数字和汉字范围的字符。这可能丢失具有语义的技术符号，也可能掩盖真实的 ASR 错误。


# W7D4 模块3：指标测试与评分规范冻结

## 1. 三种指标的完整计算流程

**CER 的计算流程：**

首先对 Reference 和 Hypothesis 使用相同的 normalize_score() 进行规范化，再去除计分空白，按 Unicode 字符划分 token，最后使用编辑距离算法评分。

```text
原始文本
  ↓
normalize_score()
  ↓
去除计分空白
  ↓
字符 token 列表
  ↓
score_tokens() / score_corpus()
  ↓
CER
```

计算公式：

$$
CER=\frac{S_c+D_c+I_c}{N_c}
$$

其中分母为 Reference 的字符数。

**MER 的计算流程：**

使用 mixed_tokens() 将文本转换为混合 token 列表。

其中 mixed_tokens() 内部已经调用 normalize_score()。

```text
原始文本
  ↓
mixed_tokens()
  ↓
规范化与混合分词
  ↓
中文单字 / 英文词 / 数字串 / 有效符号
  ↓
score_tokens() / score_corpus()
  ↓
MER
```

计算公式：

$$
MER=\frac{S_m+D_m+I_m}{N_m}
$$

其中分母为 Reference 的混合 token 数。

**English WER 的计算流程：**

根据05文档，English WER 在独立的英文子集上计算。

本次基础英文实验使用以下流程：

```text
英文 Reference / Hypothesis
  ↓
normalize_score()
  ↓
英文分词
  ↓
score_tokens() / score_corpus()
  ↓
English WER
```

本次简单英文样本使用空格分词。正式评估时需要固定英文 tokenizer，并且不能把中文样本混入英文测试子集。

计算公式：

$$
WER=\frac{S_w+D_w+I_w}{N_w}
$$

**三种指标为什么可以复用同一个编辑距离算法：**

因为 CER、MER、WER 本质上都计算 Reference token 序列与 Hypothesis token 序列之间的最小编辑距离。

它们的主要区别是 token 的定义：

- CER：字符。
- MER：混合粒度 token。
- English WER：英文单词。

因此，只需要改变 tokenizer，无须重新实现 DP 和 Backtrace。

## 3. 评分边界与注意事项

**为什么不能静默删除未知符号：**

因为符号可能包含真实语义。

例如：

```text
C++ ≠ C
GPT-4 ≠ GPT4
```

如果规范化时未经约定就删除这些符号，可能让不同文本变得相同，从而掩盖 ASR 识别错误。

因此，未知有效符号需要使用明确的 fallback 规则保留，或对无法安全处理的字符显式报错。

**为什么英文 WER 不能直接混入中文样本：**

因为中文通常没有英文那样的词间空格。

如果直接对中英混合文本使用英文空格分词，会造成计分单位不一致。

因此，英文 WER 应在独立英文子集上，采用冻结的英文分词规则计算。

中英混合语料则使用 CER 和本项目定义的 MER。

**为什么错误率可能超过100%：**

因为插入错误的数量可能超过 Reference 的 token 数。

例如：

```text
Reference:  hello
Hypothesis: hello a b
```

多出了两个 token：

$$
I=2,\quad N=1
$$

$$
ER=\frac21=200\%
$$

因此，错误率不一定处于0到100%之间，不能强行截断。

**为什么空 Reference 的插入必须计入语料级指标：**

因为模型在没有参考文本时输出额外 token，仍然属于真实的插入错误。

空 Reference 样本对总体分母贡献0，但其插入次数必须计入分子。

只要整个语料的总参考 token 数大于0，就可以计算总体错误率。

如果整个语料的总参考 token 数也为0，当前项目实现返回 None，报告时应标记 N/A。

## 4. 评分规范冻结

**为什么需要冻结评分规范：**

因为不同文本规范化和分词规则会改变 CER、MER 和 WER。

如果评估过程中随意修改规则，即使模型没有变化，指标也可能改变，使不同实验之间无法公平比较。

因此，应在正式评估前固定规则，并保留版本。

**NORMALIZER_VERSION 的作用：**

用于记录当前采用的文本评分规范版本。

当前实现为：

```python
NORMALIZER_VERSION = "w7d4-v1-draft"
```

表示仍为待冻结的初步版本。

完成正式规则检查后，可固定为明确版本，并在实验结果中记录。

**冻结后应该记录哪些信息：**

主要包括：

- normalizer_version。
- NFKC、大小写、空白和标点规则。
- 中文、英文、数字与技术表达的 tokenization 规则。
- 未知符号 fallback 规则。
- CER、MER、英文 WER 的计分单位。
- 空 Reference 与语料级聚合约定。
- 测试用例及实际结果。

还应保存 raw_text，避免丢失原始信息。

**什么时候可以修改评分规则：**

发现明确错误或需要支持新的文本类型时可以修改，但应创建新版本，补充测试并记录变更原因。

不能根据冻结测试集上的模型错误临时调整规则，以获得更好看的指标。

不同评分版本的结果应明确区分；需要比较时，应使用同一规则重新评分。

本次六组测试已经通过，但更复杂的连字符、英文缩写、复合技术表达等边界仍需在正式冻结前明确。

## 6. 模块验收

**Q1. 为什么 CER、MER 和英文 WER 能够复用 score_tokens()？三个指标的根本区别是什么？**

因为三者都是通过编辑距离计算 Reference 和 Hypothesis 之间的替换、删除和插入错误。

它们的根本区别是 token 的划分粒度不同：

- CER 使用字符。
- MER 使用中文单字、英文词、数字串等混合 token。
- English WER 使用英文单词。

因此可以使用同一个 score_tokens()，只需更换 tokenizer。

**Q2. 为什么“价格3元”与“价格三元”不能直接判为完全一致？如果自动将3替换为三，可能带来什么问题？**

因为05文档明确规定数字采用保守评分方式，不自动合并阿拉伯数字与中文数字。

虽然二者在某些上下文中表示相同数值，但不同书写方式可能对应不同的读法或表达含义。

例如：

```text
一二三
一百二十三
123
```

如果不加区分地统一数字表达，可能把实际不同的内容错误地判定为相同，掩盖 ASR 的识别错误。

因此，只能在预先确定并验证的规则下进行数字规范化，不能为了降低错误率随意转换。

**Q3. Reference 为 C++、Hypothesis 为 C，为什么 CER 有2次错误，而 MER 有1次错误？如果直接删除 ++，会产生什么后果？**

CER 按字符计分：

```python
["c", "+", "+"] → ["c"]
```

需要删除两个加号：

$$
D=2
$$

MER 将 `c++` 和 `c` 分别视为完整 token：

```python
["c++"] → ["c"]
```

只需要一次替换：

$$
S=1
$$

如果在规范化过程中直接删除 `++`，就可能把 C++ 和 C 错误地判定为完全相同，掩盖真实识别错误。

**Q4. 一个语料包含10个参考token、2次错误；30个参考token、3次错误；以及空Reference但Hypothesis有5个token的样本。语料级错误率是多少？第三条是否参与统计？**

总参考 token 数：

$$
N=10+30+0=40
$$

总编辑错误次数：

$$
E=2+3+5=10
$$

因此：

$$
\boxed{ER_{corpus}=\frac{10}{40}=25\%}
$$

第三条音频必须参与统计，因为它产生了5次插入错误。

虽然其 Reference 为空，对分母贡献0，但不能忽略它对分子的贡献。
